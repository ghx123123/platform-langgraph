# 数据中台文件管理优化调研

> 调研日期：2026-08-11  
> 目标：解决大课程目录加载卡顿、未归类文件不可见、重复请求和目录信息表达不完整。

## 1. 开源项目对比

| 项目 | GitHub 热度（调研时） | 可借鉴能力 | 本项目取舍 |
| --- | ---: | --- | --- |
| [filebrowser/filebrowser](https://github.com/filebrowser/filebrowser) | 约 35.8k stars | 文件系统式路径浏览、当前目录加载、文件操作边界清晰 | 借鉴“先目录、后内容”，不引入其用户权限和存储后端 |

## 2. 原系统问题

1. `/api/data-hub/catalog` 首屏一次返回全部课程、目录和文件块，真实样本约 1.15 MB、2.4 秒。
2. React 开发模式重复执行初始化副作用，摘要和目录请求各发送两次。
3. 1659 份文件中有 393 份没有章节字段；旧逻辑只建立已有章节单元，导致目录接口只能访问 1266 份。
4. 主目录只显示一级项目数量，教师无法确认当前单元是否已完整加载。
5. 搜索结果硬截断 100 条，容易被理解为资料缺失。
6. 大章节 JSON 未压缩，网络传输成本与文件数量线性增长。

## 3. 已采用设计

### 3.1 两阶段渐进加载

```text
课程树摘要（学期、课程、单元、统计）
        ↓
当前资料单元（文件块、目录布局）
        ↓
单文件详情或原页预览
```

- 首屏调用 `GET /api/data-hub/catalog?summary_only=true`。
- 当前单元调用 `GET /api/data-hub/catalog?unit_id=...`。
- 切换章节只加载目标单元，不重新返回整个资料库。
- 请求使用序号控制，快速切换时旧响应不能覆盖新目录。

### 3.2 完整性修复

- 有章节资料继续进入对应章节。
- 无章节资料统一进入“全课程”单元。
- 真实课程现在显示 10 个单元，单元材料数合计严格等于 1659。
- 搜索不再截断前 100 条。

### 3.3 性能与反馈

- React Strict Mode 初始化请求去重。
- 目录加载时课程树先显示，主区显示“正在读取当前资料单元”，不再整页空白。
- 目录栏显示“已载入 X/Y 份 · 当前目录 N 项”。
- 布局匹配由逐文件线性扫描文件夹改为集合查找。
- 后端启用 GZip；最大章节 523,196 B 压缩为 33,254 B。

## 4. 真实数据结果

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 首屏目录接口 | 约 2,423 ms | 约 125 ms |
| 首屏响应体 | 约 1.15 MB | 约 3.3 KB |
| 最大章节文件数 | 随整库返回 | 583 份按需返回 |
| 最大章节网络传输 | 约 523 KB | 约 33 KB（GZip） |
| 可访问文件数 | 1266 / 1659 | 1659 / 1659 |
| 开发模式初始化请求 | 4 次 | 2 次（摘要 + 当前单元） |

## 5. 后续扩展条件

- 单个实际目录超过 1000 行时，引入 TanStack Virtual，仅渲染可视区。
- 课程数量明显增加时，将课程摘要和材料索引从完整 archive JSON 中拆分，避免每次读取所有课程正文元数据。
- 单文件详情 P95 超过 100 ms 时，建立 `block_id → archive/material` 直接索引，取消详情接口的目录重建。
- 需要跨设备恢复位置时，将当前课程、单元、目录路径和排序写入 URL，而不是只依赖页面状态。
